## Quick Start

```bash
# install globally
npm install -g config2ts

# convert the config files in the current directory
config2ts

# specify the directory and output file name
config2ts -d ./config -n config.ts
```

## Install

```bash
# install globally
npm install -g config2ts

# install as a dev dependency in a project
npm install config2ts --save-dev
```

## Command Line Usage

```bash
config2ts [options]
```

### Options

| Option | Short | Description | Default |
| :--- | :--- | :--- | :---: |
| `--name <name>` | `-n` | Output file name (single mode) / index file name (split mode) | `csv.ts` |
| `--dir <path>` | `-d` | Config directory | `.` |
| `--outDir <path>` | `-o` | Output directory | same as config directory |
| `--assets <path>` | `-a` | Asset directory; scans and generates the `assets.ts` index (optional, skipped if omitted) | none (not generated by default) |
| `--mode <mode>` | `-m` | Output mode: `single` merges into one file / `split` writes one file per table plus `index.ts` | `single` |
| `--version` | `-V` | Print version number | - |
| `--help` | `-h` | Show help | - |

### Usage Examples

```bash
# use defaults
config2ts

# specify the config directory
config2ts -d ./config

# specify the output directory
config2ts -d ./config -o ./dist

# customize the output file name
config2ts -n myConfig.ts

# full example
config2ts -d ./config -o ./src/types -n config.ts
```

## Output Modes (single / split)

Choose the output mode with `-m, --mode`. The same set of source tables under this repo's
[`config/`](https://github.com/livingyang/config2ts/tree/master/config) directory ships examples for both modes, so you can compare them directly:

- single mode example: [`config/total.ts`](https://github.com/livingyang/config2ts/blob/master/config/total.ts)
- split mode example: [`config/split/`](https://github.com/livingyang/config2ts/tree/master/config/split)

**single mode (default)**: merges all config tables into one file (`-n` sets the file name, default `csv.ts`).

```bash
config2ts -d ./config -o ./src/types -m single -n config.ts
```

**split mode**: writes one `.ts` file per table (named after the source file, e.g. `skill.csv` → `skill.ts`) and auto-generates an `index.ts` that re-exports every table and `assets.ts`. Cross-table `Ref`/`RefEnum`/`Template` references are resolved by injecting `import` statements at the top of the referencing file, so every table can be imported independently and is tree-shakable.

```bash
config2ts -d ./config -o ./src/types -m split
```

- In split mode `-n` is reused as the index file name; if you keep the single-mode default `csv.ts`, it is automatically changed to `index.ts` (unless you pass `-n` explicitly).
- `-a` is optional; omit it to skip `assets.ts`.

split mode output layout under `dist`:

```
dist/
  z-base.ts        # export namespace ZBaseCsv { ... }
  a-user.ts        # import { ZBaseCsv } from "./z-base"; export namespace AUserCsv { ... }
  skill.ts
  ...
  assets.ts        # generated only when -a is given
  index.ts         # export * from "./z-base"; export * from "./a-user"; ...; export * from "./assets";
```

> In both modes, referenced tables are always emitted before the tables that reference them (topological order by reference relationship); missing/circular references print the same warnings as before.

## Supported Config Formats

### CSV

The first row of a CSV is the field names, the second row is the field types, and data starts from the third row.

```csv
id,name,age
Index,String,Number
1,Alice,25
2,Bob,30
```

### INI

```ini
num = 1
str = string
bool = true

[ItemType]
book = 1
fruit = 2
```

### TOML

```toml
num = 1
str = "test"

[ItemType]
book = 1
fruit = 2
```

## CSV Field Types

| Type | TypeScript Type | Description |
| :--- | :--- | :--- |
| `Index` | `string` | Index field, used to generate the Map |
| `String` | `string` | String type |
| `Number` | `number` | Number type, supports `Infinity` and `NaN` |
| `Boolean` | `boolean` | Boolean type |
| `Enum` | union type | Enum type, values auto-extracted |
| `EnumIndex` | union type | Enum type used as the index |
| `String[]` | `string[]` | String array |
| `Number[]` | `number[]` | Number array |
| `Enum[]` | union type array | Enum array |
| `Object` | object type | Parses `key:value,key:value`, infers value types |
| `Object[]` | object array | Objects separated by `;`; inside an object `key:value` separated by `,`; n separators → n+1 objects, empty object slots become `{}` |
| `Ref[file]` | `TableName.Record` | References a whole row of another table; value is the target row's Index, generates `TableName.Map["id"]` |
| `Ref[file][]` | `TableName.Record[]` | Reference array, comma-separated Indexes, generates `[TableName.Map["id"],...]` |
| `RefEnum[file.field]` | `TableName.FieldName` | References an enum field of another table |
| `RefEnum[file.field][]` | `TableName.FieldName[]` | References an enum array field of another table |
| `Template[file]` | `TableName.Record` | Template inheritance: takes one row of the target table as a prototype and overrides some fields; cell `id\|key:value,...`, arrays/objects wrapped in `[..]`/`{..}`; identical to `Ref[file]` when no overrides |
| `Template[file][]` | `TableName.Record[]` | Template array, entries separated by `;` (same as `Object[]`) |

### Type Notes

- **Number**: supports `Infinity` and `NaN`.
- **Enum**: supports the empty-string type.
- **Enum[]**: the union contains every value actually present in the data (including `""` for empty slots).
- **EnumIndex**: generates an index type, uses the Enum type to build the interface, and also generates the Map.
- **Object**: cell format is `key:value,key:value` (e.g. `num:1,str:ab`); value type auto-inferred as number/boolean/string; keys across all rows are merged into one dedicated type.
- **Object[]**: objects are separated by **semicolon `;`** (commas are reserved for `key:value` inside an object, same rule as `Object`; stray empty `key:value` pairs are ignored). E.g. `num:1,,str:a;num:2` produces `[{num:1, str:'a'}, {num:2}]`; an empty object slot between separators (`a:1;;b:2`) is kept as `{}` by the n+1 rule (a bare `;` produces `[{},{}]`), an empty cell is `[]`; keys across all rows are merged into the element type, field type is `TypeName[]`.
- **Array separators and empty-data convention**: primitive arrays (`String[]`/`Number[]`/`Enum[]`/`RefEnum[...][]`) use **comma `,`** as element separator; `Object[]` uses **semicolon `;`** as object separator (commas are already used for the in-object `key:value` pairs). Raw cell values are normalized (`\r\n`/`\r` unified to `\n`, surrounding whitespace trimmed); an empty cell generates `[]`; otherwise n separators make n+1 slots and every slot is kept (including interior or trailing ones) so parallel arrays stay index-aligned. Empty slots use the type's own zero value — `''` for String/Enum/RefEnum, `0` for Number, `{}` for empty Object slots; `null` is never generated.
- **Line breaks**: `String` fields preserve line breaks inside the cell (multi-line text, the cell must be quote-wrapped in CSV) and emit `\n` in the generated code; in **structural fields a line break is equivalent to its separator** — in primitive arrays / Object key:value pairs / Template override pairs a line feed equals a comma (e.g. `a\nb` → `['a','b']`, `num:1\nstr:x` → `{num:1,str:'x'}`), and in `Object[]` / `Template[]` a line feed equals a semicolon (one entry per line works, a blank line is an empty slot by the n+1 rule). Scalar fields (Number/Boolean/Enum/EnumIndex/single Ref) have no separator semantics, so a line break there prints a warning and must be removed.
- **Unrecognized types**: a misspelled type name etc. falls back to `string` and prints a warning at conversion time.

### Generated Structure

Each CSV file generates a namespace containing:

- enum type definitions (if there are Enum fields)
- the `Record` interface
- the `List` data array
- the `Map` index (if there is an Index or EnumIndex field)

```typescript
export namespace DataCsv {
    export type mytype = "type1" | "type2";
    export const mytypeList: mytype[] = ["type1", "type2"];

    export interface Record {
        id: string;
        name: string;
        mytype: mytype;
    };

    export const List: Record[] = [ ... ];
    export const Map: { [id: string]: Record } = {};
}
```

## Reference Features

### Ref — reference another CSV's Record

Use `Ref[fileName]` to reference a data record from another CSV file.

**Syntax:**
```csv
refField
Ref[other.csv]
```

**Generated code:**
```typescript
export interface Record {
    refField: OtherCsv.Record;
};

export const List: Record[] = [
    {
        refField: OtherCsv.Map["key"],
    },
];
```

### Ref[] — reference an array of Records from another CSV

Use `Ref[fileName][]` to reference multiple rows of another CSV at once (comma-separated target row Indexes), suited for "a group of identity-bearing sub-objects" (e.g. reward groups, wave configs); inline private structured lists should use `Object[]`.

**Syntax:**
```csv
refArr
Ref[other.csv][]
```
The cell holds comma-separated Indexes (same array convention as `String[]`; empty cell is `[]`, empty slots kept by the array n+1 rule):
```csv
"key1,key2"
```

**Generated code:**
```typescript
export interface Record {
    refArr: OtherCsv.Record[];
};

export const List: Record[] = [
    {
        refArr: [OtherCsv.Map["key1"],OtherCsv.Map["key2"]],
    },
];
```

> An empty id in the array (e.g. `"key1,,key2"`) generates `OtherCsv.Map[""]` (runtime `undefined`) and prints a warning.

### RefEnum — reference another CSV's enum type

Use `RefEnum[fileName.fieldName]` to reference an enum type of another CSV.

**Syntax:**
```csv
myType
RefEnum[data.csv.mytype]
```

**Generated code:**
```typescript
export interface Record {
    myType: DataCsv.mytype;
};
```

### RefEnum[] — reference another CSV's enum array type

Use `RefEnum[fileName.fieldName][]` to reference an enum array type of another CSV.

**Syntax:**
```csv
typeArr
RefEnum[data.csv.typearray][]
```

**Generated code:**
```typescript
export interface Record {
    typeArr: DataCsv.typearray[];
};
```

### Template — template inheritance (reference a row and override fields)

Use `Template[fileName]` to take one row of another CSV as a "prototype" and override some of its fields, suited for "base config + a few variants" (e.g. elite monsters, enhanced items), avoiding copying whole rows.

**Syntax:** the cell is `<baseRowIndex>|<key>:<value>,<key>:<value>` — before `|` is the base row id (same meaning as a `Ref` value), after `|` are the overrides, comma-separated `key:value`. Omit `|` and everything after it when there are no overrides; then it is exactly equivalent to `Ref`.

Override values support three shapes (bracket syntax mirrors the generated TypeScript; commas inside brackets are not treated as pair separators):

| Target field type | Override syntax | Example |
| :--- | :--- | :--- |
| scalar (Number/Boolean/String/Enum) | bare value | `damage:150`, `kind:attack` |
| array (Number[]/String[]/Enum[] etc.) | `[v1,v2,...]` | `Params:[6,2.07]` |
| object (Object, whole replacement) | `{k:v,k:v}` | `params:{damage:100,range:5}` |

```csv
base
Template[skill.csv]
101|damage:150,range:8
102|params:{heal:500,target:ally}
103|Params:[6,2.07]
104
```

> Array values **must be bracket-wrapped**: writing `Params:6,2.07` gets chopped at the comma (only `Params:6` is kept, `2.07` becomes a stray no-key segment) and a warning is printed suggesting `Params:[6,2.07]`.

**Generated code:** at runtime it expands to an object spread (the base row is not mutated); the field type is the target table's `Record`:
```typescript
export interface Record {
    base: SkillCsv.Record;
};

export const List: Record[] = [
    {
        base: { ...SkillCsv.Map["101"], damage: 150, range: 8 },
    },
    {
        base: { ...SkillCsv.Map["102"], params: { heal: 500, target: 'ally' } },
    },
    {
        base: { ...SkillCsv.Map["103"], Params: [6, 2.07] },
    },
    {
        base: SkillCsv.Map["104"],   // no overrides, identical to Ref
    },
];
```

**Type safety:** a typo'd override key, a value of the wrong type (e.g. an array field written without brackets becomes a scalar), or an illegal enum value all fail at tsc compile time; an empty cell, an empty base id (e.g. `|damage:1`), or a stray override segment all print a warning at conversion time.

> Override keys are written on **top-level fields** (dot-path deep merge is not supported); `{...}` object values, like the `Object` type, only support flat `key:value` (no nested array/object inside); the target table must have an `Index`/`EnumIndex` (i.e. a generated `Map`; an EnumIndex table uses the enum value as id). Table output order is auto-arranged by reference relationship — no manual filename tricks needed. These constraints are the same as for `Ref`.

### Template[] — template array

Use `Template[fileName][]` to write multiple template entries in one cell, separated by **semicolon `;`** (same element separator as `Object[]`); the rules inside each entry are identical to a single `Template`:
```csv
rewards
Template[item.csv][]
"1001|damage:200;1002|count:5;1003"
```

**Generated code:**
```typescript
export interface Record {
    rewards: ItemCsv.Record[];
};

export const List: Record[] = [
    {
        rewards: [{ ...ItemCsv.Map["1001"], damage: 200 }, { ...ItemCsv.Map["1002"], count: 5 }, ItemCsv.Map["1003"]],
    },
];
```

> An empty cell generates `[]`; n semicolons keep n+1 slots (same as other arrays); a slot with an empty base id (e.g. the middle empty segment in `1001|x:1;;1003`) prints a warning.

### Reference Example

```csv
name,dataRecord,myType,typeArr
String,Ref[data.csv],RefEnum[data.csv.mytype],RefEnum[data.csv.typearray][]
"test",1,"type1","t1, t2"
```

Generated TypeScript:

```typescript
export namespace NoIdCsv {
    export interface Record {
        name: string;
        dataRecord: DataCsv.Record;
        myType: DataCsv.mytype;
        typeArr: DataCsv.typearray[];
    };

    export const List: Record[] = [
        {
            name: 'test',
            dataRecord: DataCsv.Map["1"],
            myType: 'type1',
            typeArr: ['t1', 't2'],
        },
    ];
};
```

### Empty-Value Warnings

When a reference field's value is empty, a warning is printed at conversion time:

```
[config2ts] warning: NoIdCsv row 3 field "dataRecord" ref value is empty
[config2ts] warning: NoIdCsv row 3 field "myType" ref enum value is empty
```

`Template` fields also warn on empty cells (`template value is empty`), empty base id (`template base id is empty`), empty id slots in a template array (`template array entry N has an empty base id`), and stray override segments (`template override segment ... is not a key:value pair`, usually caused by an array value missing its `[..]` brackets and being chopped by a comma).

A line break inside a scalar field (Number/Boolean/Enum/EnumIndex/single Ref/RefEnum) prints the `contains a line break inside the cell` warning — such fields have no separator semantics, so remove the line break; line breaks in structural fields (arrays/Object/Template) are legal separators and do not warn.

Reference-relationship problems are also warned during the merge scan:

- **Circular reference**: `circular table reference detected: a.csv -> b.csv -> a.csv` — tables on the cycle may reference an undefined namespace at runtime; break the cycle by hand (remove one reference or split a table).
- **Missing referenced file**: `x.csv references "y.csv" but no config file with that name was found` — check the file name and extension spelling.

## Common Modeling Scenarios

The source files for every scenario below can be found in this repo's
[`config/`](https://github.com/livingyang/config2ts/tree/master/config) directory; the single-mode result is merged into
[`total.ts`](https://github.com/livingyang/config2ts/blob/master/config/total.ts) (a test fixture that always tracks the latest syntax), and the split-mode result is under [`config/split/`](https://github.com/livingyang/config2ts/tree/master/config/split).

### Choosing: Object[] or Ref[]?

- **Inline, private, one-off** structured lists (coordinate points, wave parameters) → `Object[]`, data written directly in the cell.
- **Identity-bearing, reusable, multi-group** objects (skills, items, reward entries) → extract into a standalone CSV table and link with `Ref`/`Ref[]`, gaining type safety and cross-table enums for free.
- An `Object` cell is **flat** `key:value` and does not support nested object/array values; when you need hierarchy, split the table.

### Scenario 1: Character–Skill–Level (heterogeneous fields + multiple value groups)

Requirement: each character has several skills; skills differ in their parameter fields; the same skill has multiple value groups (levels). Split into three tables:

**1. Skill table** [skill.csv](https://github.com/livingyang/config2ts/blob/master/config/skill.csv) — heterogeneous parameters folded into an `Object` field, keys merged across all skills, missing fields become optional:

```csv
id,name,kind,params
Index,String,Enum,Object
101,fireball,attack,"damage:100,range:5,element:fire"
102,heal,support,"heal:200,target:ally"
```

Generated type (fireball has no `heal`, heal has no `damage`, both optional):

```typescript
export type params = {
    damage?: number; range?: number; element?: string;
    heal?: number; target?: string;
};
```

**2. Level-value table** [skilllevel.csv](https://github.com/livingyang/config2ts/blob/master/config/skilllevel.csv) — each row is "skill × one value group", linked back to the skill with `Ref[skill.csv]`:

```csv
id,skill,level,damage,heal,manaCost
Index,Ref[skill.csv],Number,Number,Number,Number
1,101,1,100,0,20
2,101,2,150,0,30
3,102,1,0,200,40
```

Consume side, group values by skill:

```typescript
const lv2 = SkilllevelCsv.List.filter(lv => lv.skill === SkillCsv.Map["101"])
                              .find(lv => lv.level === 2);  // damage 150
```

> If the values differ by "the level the character learned" rather than being intrinsic skill growth, build another character–skill link table (`Ref[unit.csv]` + `Ref[skill.csv]` + `level`); do not store levels directly in the character table.

**3. Character table** [unit.csv](https://github.com/livingyang/config2ts/blob/master/config/unit.csv) — references multiple skills with `Ref[skill.csv][]`:

```csv
id,name,skills
Index,String,Ref[skill.csv][]
1,hero1,"101,102"
```

Generates `skills: SkillCsv.Record[]`, data is `[SkillCsv.Map["101"], SkillCsv.Map["102"]]`, giving you the skill objects directly at runtime.

> **File order**: the tool scans all `Ref`/`RefEnum`/`Template` references and topologically sorts them automatically — referenced tables are always emitted before the tables that reference them, so manual filename ordering is no longer needed (old tricks like the `!` prefix are obsolete); tables without a reference relation keep alphabetical order. A detected cycle (A→B→A) prints a warning naming the cycle; you must break it by hand.

### Scenario 2: Description Localization (i18n)

Principle: **store only translation keys and templates in config tables, never hard-coded text; all values go through named placeholders filled at runtime.**

One CSV per language ([lang-en.csv](https://github.com/livingyang/config2ts/blob/master/config/lang-en.csv) / [lang-zh.csv](https://github.com/livingyang/config2ts/blob/master/config/lang-zh.csv)), key convention `{type}.{id}.{field}`:

```csv
id,text
Index,String
skill.101.name,Fireball
skill.101.desc,"Deals {damage} fire damage to enemies within {range} meters."
```

The two files share the same key set and generate two namespaces of identical shape (`LangEnCsv.Map[key].text` / `LangZhCsv.Map[key].text`). At runtime a single helper does the lookup and placeholder fill (placeholder names match the skill params / level table field names):

```typescript
const tables = { en: LangEnCsv, zh: LangZhCsv } as const;
let locale: keyof typeof tables = "en";

export function t(key: string, params?: Record<string, string | number>): string {
  let tpl = tables[locale].Map[key]?.text ?? key;      // fall back to key on missing translation
  if (params) {
    tpl = tpl.replace(/\{(\w+)\}/g, (_, k) => k in params ? String(params[k]) : "");
  }
  return tpl;
}

t(`skill.${skill.id}.desc`, lv);  // lv from the skilllevel table → "Deals 150 fire damage to enemies within 5 meters."
```

Conventions:

- One template shared across a skill's levels; level-specific copy adds a key layer (e.g. `skill.101.desc.lv2`).
- **Cells support real line breaks** (Alt+Enter in Excel, quote-wrapped multi-line cells in CSV): `String` field line breaks are kept as `\n`; in structural fields a line break is equivalent to a separator (a line break between array elements / key:value pairs equals a comma, a line break between template-array entries equals a semicolon), so designers can lay out "one per line"; only scalar fields like Number/Boolean/Enum/single Ref don't support line breaks (warned at conversion).
- An empty cell for a missing translation → `text: ''`, detectable in the helper for fallback/warning.
- All player-facing text — enum display names, item names, buff names — goes through the language table uniformly.

### Scenario 3: Base Row + Variants (Template Inheritance)

Requirement: many config rows differ in only a few fields (normal/elite/boss monsters, pre/post-enhancement items). Put the shared config in a base table and let variant rows reference the base row with `Template`, writing only the differing fields, avoiding copy-then-miss edits.

```csv
# monster.csv — base monster table
id,name,hp,damage
Index,String,Number,Number
m1,goblin,100,10
m2,orc,300,25
```

```csv
# monsterelite.csv — variant table (output order auto-arranged by reference)
id,name,base
Index,String,Template[monster.csv]
e1,goblin-elite,"m1|hp:250,damage:20"
b1,orc-boss,"m2|hp:2000,damage:80"
```

The generated `base` field is typed `MonsterCsv.Record` and at runtime is `{ ...MonsterCsv.Map["m1"], hp: 250, damage: 20 }` — the base row is not mutated, the variant has the full set of fields, and the consumer need not distinguish "prototype" from "variant":

```typescript
for (const v of MonstereliteCsv.List) {
  console.log(v.name, v.base.hp, v.base.damage);  // fields identical to the base table
}
```

Conventions:

- Variants only override **top-level flat fields**; when the difference itself is a set of identity-bearing, reusable data (skills, drop entries), still split the table and use `Ref`.
- Use `Template[file][]` when one row needs to carry multiple variant objects (`;` separates entries).
- A typo'd override key or wrong value type fails at tsc compile time, not at runtime.

## Asset Index (assets2ts)

Use `-a, --assets <path>` to specify the asset directory (optional; omit to skip `assets.ts`). The tool recursively scans the directory and generates `assets.ts` in the output directory:

```bash
config2ts -d ./config -o ./src/types -n config.ts -a public
```

The generated `ASSETS` constant is nested by directory structure; each file is `{ path, type }`:

- `path` is the relative path; `type` is the lowercase extension (e.g. `'png'`, `'mp3'`, `'svg'`).
- File and directory names are used as-is (e.g. `Direction.png` → `Direction`); keys with special characters are auto-quoted.
- A directory with 2+ files of the same extension gets a dedicated type (e.g. `PngAsset`, `Mp3Asset`) annotated with `satisfies Record<string, XxxAsset>`; a directory with ≤1 file or mixed extensions gets no type annotation.
- Nested directories are supported (e.g. `public/sub/image/`).

```typescript
import { ASSETS } from "./assets";

const meta = ASSETS.public.image.Direction;
// meta.path → 'public/image/Direction.png'
// meta.type → 'png'
```

## FAQ

### How do I integrate this into a CI/CD pipeline?

Add a build script in `package.json`; in CI, install dependencies first then run the conversion:

```json
{
  "scripts": {
    "build:config": "config2ts -d config -o src/types -n config.ts",
    "build": "npm run build:config && tsc"
  }
}
```

### Is there a watch mode (auto-regenerate on config change)?

No built-in watch mode yet; you can use a file watcher:

```bash
npx nodemon --ext csv,ini,toml --exec "config2ts -d config -o src/types -n config.ts"
```

### Does it support nested data structures?

`Object` / `Object[]` only support flat `key:value` pairs (values inferred as number/boolean/string), not objects nested inside objects. For deep nesting:

- Use INI or TOML format (natively supports nested tables).
- Split the data into multiple CSV files and link them with `Ref` / `RefEnum`.

### The generated code has type errors or the data is not as expected — what now?

1. Watch the conversion warnings: unrecognized types (e.g. a typo) fall back to `string` with a warning; empty `Ref`/`RefEnum` values and empty id slots in `Ref[]` also warn.
2. Check the first two CSV rows (field-name row, type row) are correct; fields containing commas must be quote-wrapped.
3. Generated files carry a `DO NOT EDIT` header and are fully overwritten on every conversion — do not hand-edit generated files.

## Notes

1. **Output mode**: by default `single` mode merges all config files into one TypeScript file; with `-m split` each table becomes its own file plus an auto-generated `index.ts` that re-exports all tables and `assets.ts`.
2. **Namespace**: each config file generates an independent namespace, named with the PascalCase form of the file name.
3. **BOM support**: UTF-8 files with a BOM are handled automatically.
4. **Empty rows**: empty rows in a CSV are filtered out (when an Index field is present).
5. **Reference order**: the tool scans `Ref`/`RefEnum`/`Template` references and topologically sorts them, guaranteeing referenced tables are emitted before referencing tables; tables without a reference relation keep alphabetical order, so no manual naming is needed to control order.
6. **Reference path**: the referenced file must be in the same directory.
7. **Template overrides**: the cell uses `|` to separate the base row id from overrides (`id|key:value,key:value`); `Template[]` uses `;` to separate entries; scalar values are bare, array values must be wrapped in `[..]` (e.g. `Params:[6,2.07]`), object values use `{..}` for whole replacement; overrides are top-level flat fields, dot-path deep merge is not supported; the target table's fields are not validated at conversion time, but a wrong key name or value type is reported at tsc compile time.
8. **Line breaks**: `String` field line breaks are kept as `\n`; in structural fields (array/Object/Object[]/Template/Template[]) a line break equals the corresponding separator (comma or semicolon), supporting "one per line" layout, and a blank line becomes an empty slot by the n+1 rule; a line break inside a scalar field (Number/Boolean/Enum/single Ref) warns at conversion and must be removed; multi-line cells must be quote-wrapped in CSV.
9. **Large-table downgrade**: tables with more than 1000 rows have the `EnumIndex` field that serves as the unique key downgraded from an enum union to `string` in the `Record` (other fields unchanged); this makes every row object literal share one type, avoiding the tsc `ts(2590) Expression produces a union type that is too complex to represent` error that occurs when a single `List` array literal contains too many object literal types. The `key` union type and `keyList` are still generated normally (they do not trigger the limit), so cross-table `RefEnum` references are unaffected; the cost is that the key field of that large table loses literal-level type checking.
